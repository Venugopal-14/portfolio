DeployHub — Deployment Automation

Platform engineering for Kubernetes deployment automation across distributed environments.

Part of my professional work at BT Group. Internal architecture, credentials and confidential details are intentionally omitted.

Overview & problem

Across multiple PreProd and Production environments, Kubernetes application deployments were manual and inconsistent — slow to run, hard to repeat, and prone to configuration drift. The goal was repeatable, one-click deployments with validation built in.

My role & contributions

  • Owned the deployment-automation workflow: Jenkins pipelines, Ansible roles and GitLab integration.
  • Designed Kubernetes namespaces, deployments, services, ingress, secrets and configuration management.
  • Authored reusable Python/Ansible frameworks for one-click provisioning.

Architecture

GitLab → Jenkins → Ansible → Kubernetes → Validation

Workflow

  • Code/config changes in GitLab trigger a Jenkins pipeline.
  • Ansible applies Kubernetes manifests and configuration consistently across environments.
  • HAProxy ingress routing and post-deploy validation confirm the release is healthy.

Challenges & solutions

  • Config drift: standardized reusable Ansible roles so every environment deploys identically.
  • Slow provisioning: one-click automation reduced provisioning from days to under an hour.
  • Reliability: added deployment validation and ingress checks to catch failures early.

Enterprise Project · BT Group

AutoOps AI — AIOps & Self-Healing Platform

An enterprise AIOps initiative for intelligent incident analysis and human-approved remediation.

Associated with my engineering work at BT Group. Confidential internal infrastructure details are intentionally omitted.

Overview & problem

High alert volume and manual triage made incident response slow and noisy. AutoOps AI reduces that noise and assists engineers with context-rich analysis — while keeping humans in control of any remediation.

My role & contributions

  • Built FastAPI services and background workers for the ingestion and analysis pipeline.
  • Implemented fingerprint-based deduplication and alert-to-incident correlation.
  • Integrated LLM reasoning (Ollama) with operational context for analysis.

Architecture

Alerts → Dedup → Correlate → LLM Analysis → Approve → Remediate → Validate

Workflow

  • Ingestion & dedup: continuous alert ingestion with fingerprint-based deduplication.
  • Correlation: alert-to-incident correlation, assignment and severity-based SLA tracking.
  • LLM reasoning: Ollama (LLaMA3/Qwen) with Prometheus data and incident context for root-cause and remediation suggestions.
  • Approved remediation: executed through Jenkins jobs and Ansible playbooks after human approval.
  • Recovery validation: post-remediation checks via Prometheus with full audit logging.

Challenges & solutions

  • Alert noise: fingerprint deduplication collapses duplicate signals.
  • Safe automation: remediation always requires human approval before execution.
  • Query load: PromQL query caching reduces repeated monitoring calls.

Technology stack

PythonFastAPIBackground WorkersOllamaLLaMA3 / QwenPrometheus / PromQLJenkinsAnsibleMySQL

Learnings

  • LLMs are most useful as an analysis copilot with a human-in-the-loop guardrail, not for autonomous action.
  • Good deduplication and correlation matter more than model choice for reducing noise.
